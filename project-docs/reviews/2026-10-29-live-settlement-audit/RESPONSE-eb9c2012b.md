## B2：默认 unit 缺少两处守卫覆盖——成立，已补

`usage_stats_guard_unit_test.go` 调用生产 `Fail`，独立匹配实际执行 SQL 的 owner/fence/generation/state 谓词，并分别验证影响一行和零行的返回值；不依赖生产 SQL 常量自我比较。趋势测试调用两个公共生产入口，检查完整性错误仍然可识别且没有数据返回，禁止吞错回扫 raw。

用 Go overlay 分别撤去实际 Fail 的状态谓词及趋势提前返回，对应新 unit 均失败；恢复后通过。这两处防护在无数据库环境也能被锁住。

## D1：按用户确认实现部分可用

API 新增 `usage_availability`，分别标明累计、今日、当前小时、近五分钟指标是否完整。不完整的对应数值序列化为 JSON `null`，其他安全指标和用户/API Key/账号卡片继续返回。保留的隔离日旧桶不作为当前累计值输出，隔离状态也不会自动解除。

聚合关闭时的 raw 仪表盘同样检查原始数据安全边界。升级当天即使尚未产生队列行，今日边界也会检查；缺少完整性控制时只保留实体卡片。真实数据库回归覆盖了公开聚合入口、raw 范围入口及控制行缺失。

snapshot 对不完整图表范围返回 `unavailable_sections`，省去对应数据；图表缺失不再导致所有卡片一起报错。查询检查和数据读取使用同一 REPEATABLE READ 只读事务，绕过分段缓存，仅缓存整个 snapshot，避免拼接不同版本的数据；服务只复制不可变配置。Redis stats cache key 升为 v2，防止旧版本无状态缓存被误用。部分可用状态、null 值和 uptime 经新建响应及缓存响应验证。

管理页面显示中文/英文部分可用提示及「不可用」值，不把 null 格式化成 0。不完整范围显示明确图表占位，并停止该范围的附加用户趋势/排行榜请求；切换到完整日期后恢复展示。中英文 key、页面状态和日期恢复已有渲染回归。

这是有意的 API 契约变化：消费方必须接受用量指标为 null，前后端应配套发布。金额和用量仍按既有业务口径，不修改账本、迁移或 Live 协议。

D1 对支付/账号用量的波及判断也需缩小：`payment_stats.go` 中同名方法读取 PaymentOrder，属于 PaymentService；`account_usage_service.go` 的命中是通用 UsageLogRepository 接口声明，不能当成实际调用证据。本轮没有修改这些独立功能。
