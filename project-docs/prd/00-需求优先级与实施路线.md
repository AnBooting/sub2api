# Sub2API 优化：需求优先级与实施路线

版本：1.2｜日期：2026-10-10｜用途：正式开发评审基线

## 1. 目标与依据

在保留现有用户、额度与业务入口的前提下，解决价格单位混乱、账号负载不均、站点故障直接暴露、充值体验割裂及图片视频能力不足。能配置解决的不开发；上游已有能力优先升级/移植；现有状态、订单、价格、告警、调度能力优先扩展，仅补缺口。只有现有能力确实无法满足时才新增模块。

本文件与 PRD-01～06 是产品经理制定的项目产品方案，用于与甲方再次对齐，并指导前后端开发和验收。Credit 基础计价、国模 LiteLLM CNY 价格源、外模沿用 Sub 当前 USD 价格源、DeepSeek 峰谷价、用户主动开启高倍率兜底、云猫完全白标、图片回迁及视频按次/按秒方向属于甲方已确认的核心业务口径；实施优先级、阶段顺序、调度策略抽象、异常交互、最小开发原则及详细验收由产品经理制定。原始诉求与确认清单用于追溯，冲突旧稿不再作为开发依据。

| 依据 | 用途 |
|---|---|
| 《sub优化原始需求.txt》 | 六项原始诉求的范围追溯 |
| 《17-prd-v1.md》 | 历史评审材料，当前实现需在实施前核查 |
| 《Sub2API 中转平台优化——需求确认清单.md》 | 确认事项的追溯；备选方案以最终决策为准 |
| 甲方已确认核心业务口径 | 核心业务方向依据 |
| 产品经理制定的产品方案 | 实施优先级、阶段、交互、分工与验收依据 |
| 参考产品形态 [ovo1.vip](https://ovo1.vip) | 仅作交互参考，不作为接口能力依据 |

实施前需核查当前 Sub2API 实现、部署配置与外部接口。下述复用对象是实施核查方向，不能替代当前代码和运行状态的验证。

## 2. 冻结业务基线

| 主题 | 最终规则 |
|---|---|
| Credit | 充值 ¥1 可获得 1 Credit；站内余额、额度与消费统一以 Credit 表达 |
| 价格来源 | 国内模型人民币价格统一使用 LiteLLM 提供的 CNY 价格数据，国外模型沿用 Sub2API 当前 USD 价格源；优先复用现有 LiteLLM / Sub2API 同步能力，不为国内厂商分别建设官方价格采集接口，也不要求逐个 OpenAI / Anthropic / Google 抓取官方价 |
| 价格同步 | 周期由管理员配置；失败保留 Last Known Good Price 继续服务，记录异常并复用 Alert / Email 通知管理员，持续故障避免高频重复通知 |
| 计费 | CNY/USD 源价格数值直接映射为同数 Credit，不换汇；消费＝模型基础 Credit 单价×实际服务分组倍率×使用量；多计费项分别计算后求和 |
| 历史数据 | 站内额度仅改单位语义，数值不换算、不按新价回算；真实支付继续 CNY，源价格保留原币种 |
| 调度 | 会话亲和＋健康状态＋当前负载/并发容量＋全局/分组策略；本期无账号权重或账号优先级需求；先组内换号再按用户顺序换普通组，仅站点侧可恢复故障触发，关键参数不变 |
| 高倍率兜底 | 管理员按模型提供可选高可用分组，用户主动开启；这是额外稳定性能力及增值推荐入口，不依赖独立分组访问权限 |
| DeepSeek | 价格金额来自 LiteLLM CNY 数据，峰谷时段、时区和政策规则按 DeepSeek 当前有效官方政策；同分组自动切基础价，请求开始锁价 |
| 充值 | 云猫是商品、订单、支付和卡密后台能力来源；本站仅做完全白标展示与最小适配，不重建支付、手续费、财务及清结算系统；必要时允许非公开接口，交付卡密不自动兑换 |
| 商品同步 | 云猫为商品主数据源；同步失败保留展示数据、暂停新购买，恢复后恢复购买 |
| 交付异常 | 云猫支付成功但卡密未获取时展示“已支付 / 交付异常”、本站/可追踪订单号和联系站长提示，站长通过云猫后台或接口处理 |
| 多媒体 | 图片迁移现有图片站能力；视频新增透传与计费，Seedance 为首批候选 |
| 视频模式 | 本期仅冻结 `per_request` / `per_second`，按模型×分组配置且每组合一种；其他维度仅按首批 Provider 的真实必要性最小适配，不预建通用多维视频计费系统 |

## 3. 与旧稿的替代关系

| 旧稿内容 | 本期处理 |
|---|---|
| 全站人民币展示、外币按汇率转换 | 由 Credit 方案替代，删除汇率同步与换算需求 |
| 云猫 iframe、默认直接到账、非公开接口仅二期 | 改为本期完全白标与卡密交付，非公开接口是必要时的可选实现路径 |
| 默认强制高倍率兜底 | 改为普通分组排序＋用户主动开启高可用兜底，不引入分组访问权限体系 |
| 视频模式仅按模型配置 | 改为模型×分组唯一计费模式 |
| 需求 1/5 只验证、不修改 | 本期 PRD 定义目标行为；先核查已有实现，符合则仅验证，不符合才最小修改 |
| 全量对齐 new-api 及旧稿全部媒体模型 | 不承诺全量兼容；现有图片迁移清单及确认的视频批次界定范围 |
| 沉默即通过 | 不作为确认方式；明确确认与验收证据才构成依据 |

实施前需核查当前版本、迁移序列、账号配置、商品范围及外部接口，不直接沿用旧稿的现状数字或性能阈值。画布、历史订单导入、独立补单/调账改造、订阅与并发权益售卖不纳入本期。

## 4. 优先级与实施路线

本项目当前实施优先级由产品经理根据已确认业务目标确定如下：P0 为 PRD-01、PRD-05、PRD-02；P1 为 PRD-04、PRD-03；P2 为 PRD-06。第一优先避免错计费和亏损，第二优先提升核心请求可用性，随后补高可用与充值体验；图片/视频属于业务回迁和能力扩展。共享计费与调度先统一契约。

| 阶段 | 优先级与交付 | 前置条件 | 阶段验收 |
|---|---|---|---|
| A：现状核查 | 六项复用清单与缺口 | 实际版本、源码、脱敏配置、图片站调用样例、云猫资料 | 每项指向现有代码/配置和可观察行为；无依据的现状不写成结论 |
| B：计费正确性 | P0 PRD-01、PRD-05 | LiteLLM 国模 CNY 数据、Sub 外模 USD 数据、Credit 映射、DeepSeek 官方峰谷规则及既有倍率粒度/历史额度语义核实 | Credit 公式、历史数值不变、同步告警与官方时段锁价通过 |
| C：核心稳定性 | P0 PRD-02 | B 的实际分组结算契约 | 全局/分组策略、并发约束、亲和与可恢复故障转移通过 |
| D：增强能力 | P1 PRD-04、PRD-03 | 04 依赖 B/C；03 依赖商品与支付接口及 B 的额度语义 | 主动授权兜底、白标商品同步、可信支付与卡密交付异常兜底通过 |
| E：业务回迁 | P2 PRD-06，先图片迁移再首批视频 | B/C；视频协议、计价规则与时长证据落实 | 原图片调用回归；视频中转、两模式与不同分组定价通过 |
| F：集成、回归、发布验证 | 本期集成结果 | 各 PRD 验收通过及实际部署资料 | 数据副本升级与回滚演练、接口兼容、跨功能账单核对完成 |

不以日期估算替代排期。云猫接口适配和视频厂商接入的工作量，在资料与样例核实后确定。

## 5. FE / BE 交付边界

| 层 | 交付内容 | 汇总验收 |
|---|---|---|
| FE | 单位修正、Key 分组排序、调度策略选择、兜底主动开启、商品同步状态、白标充值与交付异常提示、价格/任务展示 | CNY/Credit 明确；当前倍率可见；商品服务异常与联系站长路径清楚；不露云猫 |
| BE | 可配置价格同步与告警、锁价、全局/分组调度策略、能力过滤、云猫最小白标适配与用户/订单关联、媒体透传与结算 | 继承/覆盖正确；同步失败保留展示数据并暂停/恢复新购买；不重复操作或扣费，不自建支付财务系统 |

FE 不自行计算最终扣费、确认支付成功或代替 BE 校验用户/Key 归属；BE 不以新增前端页面作为接口能力的前置条件。接口字段优先沿用现有契约，仅补语义缺口。

## 6. 必须核查的交付条件

- **混合币种分组**：核实当前倍率粒度。优先按国模/外模分组经营，或复用已有模型×分组定价能力；不默认新增模型系数，也不改变冻结公式。
- **调度**：核实亲和、健康状态、当前负载/并发容量、限流、冷却及调度策略的真实实现；本期不新增账号权重、账号优先级或人工权重配置。
- **云猫**：验证商品、下单、支付状态、卡密和签名能力能否满足完全白标；无法满足时阻塞该交付，不擅自回退为 iframe。
- **DeepSeek**：核实目标模型的 LiteLLM CNY 峰/谷价格数据与 DeepSeek 官方有效时段、时区和政策；数据无法完整表达两档价格时列为接入缺口，按现有 Sub/LiteLLM 能力最小补充，不猜价或重建厂商价格采集系统。
- **多媒体**：确认图片迁移清单、Seedance 版本/渠道、任务查询方式及视频计费单价/时长来源；仅当实际 Provider 必需时补额外维度最小适配。
- **发布**：核实当前部署及数据结构，按真实版本准备备份、升级与回滚；历史账务纠错、欠费政策等额外业务决策另行确认。

## 7. 完成标准

六份 PRD 的 FE/BE 验收均有对应证据，集成后价格、服务组、用户/Key 归属、云猫订单展示与消费记录一致；没有因源码或资料缺口被猜测填入的上线参数。开发交付时分别报告“已实现、已验证、未验证”，测试通过不等于已部署。
