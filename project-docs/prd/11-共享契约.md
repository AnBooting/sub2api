## C-1 锁价快照（pricing_snapshot v2）

扩展现有 `usage_logs.pricing_snapshot`（jsonb，生成于 service/pricing_snapshot.go:7）。旧行为 v1 或 NULL，读取时按版本分支，不回填。

```json
{
  "v": 2,
  "quota_unit": "credits",
  "request_started_at": "2026-10-10T08:00:00Z",
  "price_version": "cny:2026-10-10T00:00:00Z#a1b2",
  "source": "native_cny | remote_usd | manual | channel",
  "currency": "CNY",
  "unit": "per_1m_tokens",
  "period": { "label": "offpeak", "timezone": "Asia/Shanghai", "window": "00:30-08:30" },
  "items": [
    { "kind": "input", "base_credit_price": 2.0, "usage": 500000, "normalized_usage": 0.5, "subtotal": 1.0 }
  ],
  "served_group_id": 12,
  "group_multiplier": 1.2,
  "total_credit": 1.2,
  "media": null
}
```

规则：
- `items[].kind` 取 input / output / cache_read / cache_write / cache_write_1h / image / video_request / video_second，同一用量只能归入一个 kind（S-2）。
- `period` 仅在价表含峰谷 schedule 时出现（TS-05）。
- `group_multiplier` 是**请求开始时点**的实际服务组倍率；为此请求开始时须一次性快照所有候选组倍率（C-6 `candidate_multipliers` 只存在内存/请求上下文，不落库）。
- `media` 仅 TS-06 使用：`{ "mode": "per_request|per_second", "billable_count": 1, "billable_seconds": 10, "seconds_source": "upstream|request" }`。
- 复算校验：`total_credit == group_multiplier × Σ items[].subtotal`（按现有精度）。

## C-2 价表版本与同步状态

| 字段 | 含义 |
|---|---|
| source | native_cny / remote_usd |
| version | 内容哈希 + 拉取时间，构成 `price_version` |
| status | ok / degraded（使用 LKGP）/ empty（从未成功） |
| last_success_at / last_attempt_at / last_error | 同步观测 |
| failure_streak | 连续失败次数，用于通知抑制 |

生效规则：新版本通过校验（币种、单位、模型映射、峰谷区间无空档/重叠）后**整版原子替换**；任何一项失败保留 LKGP，`status=degraded`。通知复用 `ops.alert` 邮件事件（service/notification_email_service.go:34），同一 source 在状态从 ok→degraded 时发一次，恢复时发一次，持续失败期间不重复。

## C-3 Key 分组链

现状 Key 只有单个 `group_id`（ent/schema/api_key.go:44）。新增关联表（逻辑名 `api_key_group_links`）：

| 字段 | 说明 |
|---|---|
| api_key_id, group_id | 唯一约束 (api_key_id, group_id) |
| role | `normal` / `ha`（高可用兜底） |
| position | role=normal 时从 0 递增，决定尝试顺序；role=ha 时同样排序 |
| enabled_by_user_at | role=ha 必填，记录用户主动开启时间；迁移不得写入 |

兼容：迁移把现有 `group_id` 写成一条 role=normal、position=0 的记录；`api_keys.group_id` 保留并与 position=0 保持同步，供未改造路径读取。鉴权缓存（api_key_auth_cache.go）需包含该链。
## C-4 调度策略

| 键 | 取值 | 作用域 |
|---|---|---|
| scheduling.strategy | `stable` / `balanced` / `latency` | 全局默认 |
| group.scheduling_strategy | `inherit`（默认）或上述三值 | 分组覆盖 |

有效策略 = 分组值 ≠ inherit ? 分组值 : 全局值。策略到底层参数（粘性等待、回切条件、错误容忍）的映射表由 TS-02 定义并作为代码常量评审，不暴露给站长。任何策略都不得放宽：并发硬上限、C-5 分类、关键参数保持。

## C-5 故障分类

上游尝试结果统一归入下表，**只有 retry_* 两类允许换号/换组/兜底**。

| 类 | 例子 | 动作 |
|---|---|---|
| retry_account | 上游账号鉴权失败、账号限流、账号满载、渠道能力不匹配 | 标记账号状态（复用 ratelimit_service），换号 |
| retry_transient | 连接失败、上游临时 5xx，且确认未执行或可幂等 | 换号 |
| fail_client | 本站 Key 无效、余额不足、参数错误、模型名无效 | 直接返回 |
| fail_policy | 内容审核、明确业务拒绝 | 直接返回，不换渠道 |
| fail_uncertain | 超时且无法确认上游是否执行；流已向客户端输出 | 不重发，返回明确失败 |

附加约束：流式只有在首字节写给客户端之前可重试；媒体已提交任务按 TS-06；单逻辑请求有总尝试上限（配置项）。

## C-6 逻辑请求与使用记录

`usage_logs` 每个逻辑请求只写一条成功记录，新增/复用字段：

| 字段 | 说明 |
|---|---|
| request_id | 逻辑请求 ID（复用现有 request id，幂等键） |
| requested_group_id | Key 链首组 |
| served_group_id | 实际服务组（结算倍率取它） |
| failover | none / account / group / ha |
| attempt_count | 上游尝试次数 |
| pricing_snapshot | C-1 |

尝试明细（每次的账号、分类、原因）写入现有 ops 错误日志/结构化日志，不另建表；管理员可按 request_id 追溯。用户侧接口只返回 served_group、failover、Credit，不返回账号或凭据。

## C-7 错误码（本期新增）

| code | HTTP | 场景 | 登记 |
|---|---|---|---|
| pricing_unavailable | 503 | 无有效价/缺价，调用上游前拒绝 | TS-01/05/06 |
| no_available_group | 503 | 普通组链与已授权兜底全部不可用 | TS-02/04 |
| upstream_uncertain | 504 | 超时且无法确认上游是否执行 | TS-02/06 |
| product_sync_unavailable | 503 | 商品同步异常，暂停新购买 | TS-03 |
| order_delivery_pending | 200 业务态 | 已支付、卡密未获取 | TS-03 |
| video_mode_conflict | 400 | 同模型×组配置两种模式（管理端） | TS-06 |

错误体沿用各协议 writer，`code` 放在协议允许的 type/code 字段。HTTP 状态为建议值，TS 可按现有 writer 调整但需登记。
