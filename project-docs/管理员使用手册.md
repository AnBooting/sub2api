## 1. 价格体系：源价 → 基础 Credit → 倍率 → 最终售价

### 1.1 四层口径

| 层 | 含义 | 存放位置 |
|---|---|---|
| 源价格 | 厂商/价格源给的原始价，**保留币种**（国模 CNY、外模 USD）与计量单位 | 价格管理页 / 价表数据 |
| 基础 Credit 单价 | 源价数字**等值映射**，不换汇（源价 2 → 基础价 2 Credit） | 价格管理页 |
| 分组倍率 | 商业售价杠杆；可含峰谷倍率、视频独立倍率 | 分组表单 |
| 最终售价 | 基础价 × 实际服务分组的有效倍率 | 使用记录/快照里体现 |

**充值比例固定 ¥1 = 1 Credit**，不随汇率浮动；平台也不会自动调整你的商业售价。

### 1.2 国模人民币价格源

（路径：/admin/settings → 功能开关 →「模型价格与额度计费」）

- 开关文案：「使用国模人民币价格源」。
- 提示原文：「国模使用原始 CNY 价卡，Claude/GPT 等继续使用 USD 价卡。¥1 和 $1 都扣 1 额度，不做汇率换算；充值到账比例固定为 1。缺少人民币价格的国模需配置手动价格。」
- 开关保存后**即时生效**。

### 1.3 价格同步周期

（同页：「定价同步周期（小时）」）

- 可填 1–720 的整数小时；保存后立即重排定时器，无需重启。
- 留空表示沿用配置文件默认值；页面会显示「当前生效周期：{hours} 小时」。
- **同步状态已在本卡片展示**：USD / CNY 各自「模型数 · 最近更新时间」（从未同步显示"尚未同步"），以及异常提示 `cny_error` / `usd_error` / `deepseek_calendar_error`；页面每 5 秒轮询刷新，并提供「立即同步价格」与「重试」。
- **同步失败不覆盖 Last Known Good Price**：继续用最近一次有效价服务，并记录异常、按现有 Alert/Email 能力通知管理员；同一持续故障会合并/抑制重复通知，不高频刷邮件。
- **币种/单位异常不得静默覆盖**：国模数据出现 USD、或外模数据出现 CNY、或单位映射异常时，保留当前有效价格。

### 1.4 缺价、零价与「官方内置兜底价」：三条互不相同的红线

- **缺价（未定价）**：请求在上游调用前被拒绝（**HTTP 503**，错误码 `pricing_unavailable`），**不允许零成本放行**，也没有"零价放行"开关。判定实现见 `backend/internal/service/pricing_presence.go`（`tokenPriceCompletenessError`）与 `backend/internal/handler/gateway_handler.go:2547`。
- **显式零价**：按正常价结算为 0，与缺价是两件事，在页面上要能区分。
- 媒体模型的兜底同样禁止：价格页提示「未配置时该模型拒绝放行，不会回落到其它价格。」

#### 1.4.1 「官方内置兜底价」不是缺价放行（管理员最容易搞混的一条）

上游为**部分模型**内置了该模型**自身的官方价**（硬编码在 `backend/internal/service/billing_service.go` 的 `fallbackPrices`，如 `gemini-4-argon`、`claude-haiku-5-5`）。命中这张内置表时**正常计费**，不报错。

**判定顺序**（`getUSDModelPricingAt`，`billing_service.go:1476`）：

| 顺序 | 来源 | `PricingSource` | 结果 |
|---|---|---|---|
| ① | 国模原生 CNY 价卡 | native card | 按国模价卡计费 |
| ② | LiteLLM 价卡 | `catalog` | 按价卡计费 |
| ③ | **官方内置兜底价** | `fallback` | **按该模型自身的官方价正常计费** |
| ④ | 都没有 | — | `ErrModelPricingUnavailable` → **503 `pricing_unavailable`**，不发上游 |

关键区分：

- **内置兜底价是「该模型自己的官方价」**，不是零价，也**不是"回落 GPT 兜底价"**——它按模型名/系列规则匹配**同厂商同系列**的价格（`getFallbackPricing`），不会拿 A 模型的价格去给 B 模型用。
- 因此本项目红线「缺价不得放行」**与它不冲突**：红线禁的是①**按 0 元放行**、②**回落到 GPT 兜底价**；内置兜底价两者都不是。
- **所以「缺价一律拒绝」这句话对管理员是不完整的**：准确说法是「**既没有管理员配价、也没有官方内置价**的模型才被拒」。

#### 1.4.2 用「定价状态」徽标判断某个模型为什么能计费 / 为什么被拒

管理端分组列表每行有**「定价状态」徽标**（`frontend/src/components/admin/group/GroupPricingStatusBadge.vue`，判定逻辑 `frontend/src/components/admin/pricing/priceStatus.ts`）：

| 徽标 | 含义 | 该模型会怎么算 |
|---|---|---|
| 定价完整 | 逐模型定价规则都填全了 | 按填写的单价计费 |
| N 个模型缺价字段 | 规则存在但缺价字段 | 缺价字段的模型：**有**官方内置价 → 按内置价计费；**没有** → 计费前被拒（`pricing_unavailable`） |
| 未填价 · 按官方内置价计费 | 规则只登记了模型、没填价格 | 同上：有内置价则按内置价计费，没有则被拒 |
| 未配置定价规则 | 没有逐模型规则 | 完全按渠道价格或官方内置价（价卡）计费 |

管理端「添加模型价格」旁的提示原文：

> 没填价的模型按官方内置价（价卡）计费——官方内置价是该模型自身的官方价，不是缺价放行；只有连官方内置价都没有的模型才会在计费前被拒绝（pricing_unavailable）。

### 1.5 缺价清单与价格总表

（路径：/admin/channels → 顶部视图切换「渠道列表 / 价格总表 / 缺价清单」）

- **价格总表（只读）**：汇总当前渠道与分组定价规则里出现过的模型，以及币种、计量单位与各项单价（输入价/输出价/缓存读写价/图片价），并标注价格来源（手工/缺省/价卡）与来源范围（渠道/分组/默认价卡）。支持按模型名与币种过滤。
- **缺价清单**：列出**已配置但价格不完整**的模型，每行说明缺什么（输入价/输出价/缓存价/图片价）、探测结论，并给「去定价」跳转（渠道级跳到该模型的定价编辑处；分组级只能到分组管理页）。
- **检测口径（重要）**：两个视图里的「默认价卡」一列是**前端按当前默认价卡逐模型探测**的结果（`GET /admin/channels/model-pricing`），**可能与实际计费存在差异**，不是权威结论；通配符规则不参与逐模型检测；已命中分组/渠道规则的模型按后端优先级整条规则生效。
- **覆盖范围的硬限制**：默认价卡**只提供单模型查询接口**，没有全站模型总表接口，所以价格总表只列出渠道/分组规则里出现过的模型，不代表全站模型都列全了。
- 探测是前端发起：限并发、可中断、有进度提示，探测失败不阻断页面；空态写「没有检测到缺价模型」，不是「未加载」。

### 1.6 峰谷判定与倍率

- **官方峰谷**只作用在走 DeepSeek 官方价卡的模型/分组上，判定复用计费热路径的同一份实现（`deepseekPeakMultiplierWithCalendar` / `chooseDeepSeekPricingPeriod`），**判定与计费看到同一份假日日历**。
- 判定时区固定 **Asia/Shanghai**；工作日（不含法定节假日）**09:00–12:00** 与 **14:00–18:00** 为峰价（**2 倍**），其余为谷价（**1 倍**）。
- **法定节假日日历优先**：已维护的节假日按谷价；**周末（含调休补班的周末）也按谷价**。
- 节假日日历在定价设置里按年份维护（`PUT /admin/channels/pricing/holidays`，保存需 TOTP 二次确认）。某年**既无自定义日历也无内置覆盖**时，**停用该年的官方峰谷加价**（按谷价计），并在同步状态里报 `deepseek_calendar_error`。
- **分组自定义峰谷窗口优先**：`peak_rate_enabled` / `peak_start` / `peak_end` / `peak_rate_multiplier` 是另一套机制；分组配了自定义窗口时，状态与倍率以分组配置为准。
- **状态只读暴露**：分组 DTO 下发 `deepseek_pricing_state`（`state` = peak/valley/none、`label`、`timezone`、`multiplier`），**不参与计费、不写任何状态**；用户侧分组徽标显示当前峰/谷与生效倍率，管理端分组表单同显。模型广场与可用渠道视图走各自白名单 DTO，**尚未下发该字段**。
- **「当前档位 + 下一档切换时间」尚未下发**：后端目前只给出 `state` / `label` / `timezone` / `multiplier` 四个字段，**没有**"下一档什么时候切换"这类字段（`next_peak` / `next_period` 一类字段在代码里不存在）。在字段落地前，界面与文档**不要承诺展示具体切换时刻**，只说"当前处于峰/谷"。

### 1.7 两套「峰谷」不要混（最容易出错的两个地方）

站里有**两套互不相干**的峰谷机制，配置项、判定逻辑、界面位置都不同：

| | **分组高峰时段**（我们自己的机制） | **DeepSeek 官方峰谷**（上游官方价卡自带） |
|---|---|---|
| 配置项 | `peak_rate_enabled` / `peak_start` / `peak_end` / `peak_rate_multiplier`（分组表单） | 法定节假日日历（定价设置，按年份，JSON 编辑器，保存需 TOTP 二次确认） |
| 谁决定 | **管理员**自己配的高峰窗口与倍率 | **平台按官方时段自动判定**，管理员不切档 |
| 生效范围 | 该分组自己的文本/图片倍率 | 只作用在**走 DeepSeek 官方价卡**的模型/分组 |
| 限制 | **不支持跨天**时段；**仅订阅类型分组**开放该配置 | 判定时区固定 Asia/Shanghai；工作日 09:00–12:00 与 14:00–18:00 峰价 2 倍 |
| 界面 | 管理端分组表单的峰谷倍率配置 | 分组徽标的"峰/谷"只读状态 |

- **不要把它们合成同一个徽标或同一段说明**：分组表单里配的高峰窗口是"你定的营业时间"，官方峰谷是"官方价卡现在处于什么档"。两者可能同时存在、也可能只存在其一。
- **优先级**：分组自定义窗口**优先**于官方时段（分组配了自定义窗口时，状态与倍率以分组配置为准）；没配才回落到官方判定。

### 1.8 Gemini 显式上下文缓存（cachedContents）的计费口径

显式上下文缓存是上游 0.2.17 新增的能力（接口见 `/v1beta/cachedContents`）。**它走上游自己的计费与预留链路，不经过我们的锁价快照**，所以口径与我们其它计费不同，管理员排障时按下面三条看。

#### 1.8.1 计价时点分裂（现状）

同一笔显式缓存业务，**写侧与读侧可能在不同的价格版本上**：

| 侧 | 收什么 | 按什么价收 |
|---|---|---|
| **写侧**（`create` / `patch`） | 缓存输入费 + 存储费 | **live 价卡 + 实时倍率**（按该次请求到达时的价表与倍率） |
| **读侧**（生成请求里的 `cache_read`） | 缓存读取费 | **请求建立时冻结的快照**（锁价快照里的价格版本与倍率） |

也就是说，**管理员在两次请求之间改价表或改倍率，两侧可能落在不同的价格版本上**——这是**现状**，不是 bug。

> **本轮正在把写侧也纳入锁价**（与读侧用同一价格版本与倍率）。在最终实现落地前，请以**实现结果**为准；本节先按"写侧走 live 价"记录现状。

#### 1.8.2 缓存写入费的归类边界（最容易对错账的一处）

**两件不同的事，不要混**：

| | Gemini 显式缓存的**写入** | 我们共享契约里的 `cache_write` / `cache_write_1h` kind |
|---|---|---|
| 规则 | 按 Gemini 官方规则**计入 input 用量**（上游现状，**本轮不改**） | 面向**渠道/分组手工卡**与 **Anthropic 风格**的缓存写入 |
| 在账单里体现为 | **input 用量** | 独立的缓存写入计费项（kind = `cache_write` / `cache_write_1h`） |

- 所以**不能说"我们把显式缓存的写入算成了缓存写入费"**——它在 Gemini 上是**普通 input 用量**。
- 反过来，渠道/分组手工卡上配的 `cache_write` / `cache_write_1h` 是给 **Anthropic 风格**缓存写入用的，与 Gemini 显式缓存**不是同一个东西**。
- 用户按 kind 对账时，Gemini 显式缓存的写入**不会**以 `cache_write` 出现；看到 input 用量变大是正常口径。

#### 1.8.3 `patch`（延长有效期）的预检与实扣差额

- **预检**按**请求里声明的 TTL 推进量**报价。
- **实扣**按**上游实际推进的量**结算。
- 因此 **上游给更长的 TTL → 实扣大于预检额度**；**给更短 → 少收**；差额随预留释放。
- 这是**上游链路自身的口径，本轮不收紧**，此处只作说明。

## 2. 分组计费配置

（路径：/admin/groups → 新建/编辑分组）

| 配置项 | 说明 | 注意 |
|---|---|---|
| 分组倍率 | 文本/图片等默认倍率 | 是商业售价的主杠杆 |
| 峰谷倍率 | peak_rate_enabled / peak_start / peak_end / peak_rate_multiplier | **不支持跨天**时段；与"DeepSeek 官方峰谷"是**两套独立机制**（详见 1.7），别混用、别合成同一个开关；**仅订阅类型分组**开放该配置，标准分组需切换计费类型 |
| Realtime 每分钟价格 | 分组表单「语音 / Realtime 显式定价」区块（USD），含 Voice realtime / TTS / STT 三项 | 该区块**对所有平台可见**（不再是 Grok 专属），OpenAI Live 分组也有单价入口。**分组未配置单价时**，Live 会话按**未计费**落库（后台有告警）——遇到 Live 消费为 0，先查该分组是否配了单价 |
| 视频计费 | **按量（Token）/ 按次 / 按秒 三选一**，按模型 × 分组 | 代码里三种模式是 `per_token` / `per_request` / `per_second`（`backend/internal/domain/video_price_plan.go`），**一个模型一种模式**是硬约束；按次/图片计费模式必须设置默认价格或至少一个计费层级，否则保存被拦（提示：「按次/图片计费模式必须设置默认价格或至少一个计费层级」） |
| 视频分辨率层级 | 480p / 720p / 1080p 每秒价 | 不同厂商口径不同：Seedance 按 token、Grok 按秒、MiniMax 按次 |
| 视频独立倍率 | 可选，打开后视频不叠加文本倍率 | 按模型族声明计量模式与单价更清晰 |
| 调度策略 | 继承全局 / 单独覆盖 | 见第 3 节 |

**分组配价三原则**：① 同一模型×分组只留一套口径；② 没配价就别开权限（缺价会被拒）；③ 改价只影响新请求，已锁价的请求按旧价结算。

### 2.1 分组名的本地化边界（哪些地方会翻译、哪些不会）

上游 0.2.17 给 groups 加了 i18n JSONB 列（只存译文），并让**用户侧**按 `Accept-Language` 返回译文。这条能力有明确的边界，排障时按这张表判断：

| 出口 | 是否随界面语言变化 | 说明 |
|---|---|---|
| 用户侧分组**列表类**出口：API 密钥、订阅、兑换码、用量、模型广场、可用渠道 | **会** | 按 `Accept-Language` 取译文；**译文表本身不外泄**，service 层对象不被改写 |
| **网关计费**（分组 ID + 原名） | **不会** | 鉴权缓存快照 v27 是**显式逐字段拷贝**、**不含 I18n**，结构上就无从本地化；**因此不需要为 i18n 提升缓存版本** |
| **管理端**（handler/admin） | **不会（有意为之）** | 编辑表单需要「原名 + i18n 译文表」两份，管理端一律返回原字段 |
| 用户**用量统计**里的分组名 | **不会** | 来自分组聚合行，不是分组列表出口 |
| 渠道监控**用户视图**里的分组名 | **不会** | 取监控记录里的原名；要本地化需额外查分组 |
| 网关 `/v1/usage` 的 `planName` | **不会** | 用的是鉴权快照原名，**设计如此** |

> 上面后三行是**本期不做的已知边界，不是缺陷**。改动前请先确认不会把界面语言泄漏进计费路径。

## 3. 调度：全局策略 + 分组覆盖

### 3.1 全局（/admin/settings →「网关调度设置」）

- 「调度策略」选项：**稳定优先 / 平衡 / 响应速度优先**（分组级可另选「继承全局」）。
- 策略提示：「策略影响会话复用时长与粘性等待上限，不放宽并发、安全重试或模型能力约束。」
- 「单请求最大发送次数」「单请求总预算（秒）」（默认 16 次 / 600 秒，含所有真实上游重试；更小的既有限制仍然有效）。
- 「允许未分组 Key 调度」：建议保持关闭，确保每个 Key 都归属明确分组（关闭后未分组 Key 直接 403）。
- 「平台账号自动停调阈值」：账号原生用量窗口达到百分比时临时移出调度，100 表示禁用；支持全局默认 + 单账号覆盖。

### 3.2 分组级（/admin/groups → 分组表单）

- 分组表单里的调度策略下拉支持「继承全局」与三档具体策略，并展示**当前有效策略**（继承时显示全局实际生效值）。
- 优先级：**全局策略 → 分组默认继承或覆盖 → 账号实时状态 → 最终调度**。

### 3.3 故障分类（决定换不换号）

| 情形 | 平台行为 |
|---|---|
| 上游账号/Key 失效、账号限流、满载 | 先换号；组内候选耗尽再换组 |
| 连接或上游暂时故障 | 可安全重试时同样处理 |
| 本站 Key 无效、余额不足、参数错误、模型名无效 | 直接返回错误，**不换号不换组** |
| 内容审核/业务拒绝 | 不重试、不绕道 |
| 超时且无法确认上游是否已执行 | 不盲目重发，优先幂等/查询；无法消除重复风险时返回明确失败 |

**已输出流内容的请求不重放**；图片/视频已提交任务不回退成文本重试。

### 3.4 并发与"不并发/并发过大"排查

两个字段语义不同，**不要混用**：

| 字段 | 作用 |
|---|---|
| 并发数（concurrency） | **硬上限**，原子占用与释放；<=0 表示不限制 |
| 负载因子（load_factor） | 选号时的负载分母，不填则回落并发数 |

排查口诀（对应常见"部分账号不并发、部分并发过大"）：

1. 负载因子 > 并发数 → 负载率虚低 → 一直被打满；
2. 负载因子 < 并发数 → 负载率虚高 → 被过滤掉，表现为"不并发"；
3. 粘性会话 TTL 长 + 粘性权重高 → 流量集中到少数账号；
4. 实时语音（WS）长连接也占并发槽；
5. 槽位 TTL（默认 30 分钟）会让异常退出的请求长时间占位；
6. 账号快照有秒级延迟（outbox 轮询），改完并发数先等一个刷新周期再判断。

| 已交付 | 卡密已可领取 | 无 |

### 4.2 商品同步异常

- 同步失败**不删除**最近一次成功商品数据，商品仍展示，但**服务端暂停新订单创建/购买**，页面提示「商品服务暂时不可用，请稍后重试」。
- 同步恢复后自动恢复购买；已有订单的支付核实、查询、卡密交付不受阻断。
- 用户侧商品中心会显示「上次同步：{time}」。

### 4.3 白标边界

- 用户界面、跳转 URL、嵌入资源**不得出现供应商品牌或域名**；交付异常时只给本站订单号 + 联系站长。
- 本站**不建**支付账本、财务对账、退款与清结算；云猫/渠道侧是资金口径唯一来源。
- 支付成功**不自动兑换、不自动加余额**；兑换走本站既有兑换入口，兑换码只能兑一次。

### 4.4 自建支付的退款口径：受理即扣减，收口才退

自建支付（/purchase）的退款**跟随上游 0.2.17 的语义**（上游提交 `7c6f70680`），**我们没有改动**：

- **受理时即扣减额度**：退款请求被受理时，系统就把要退的金额从用户余额（或订阅天数）里**扣掉**（`PrepareRefund` → `prepDeduct`，`backend/internal/service/payment_refund.go:208`）。因此**用户看到的余额在退款受理后就已经少了**，这是预期行为，不是重复扣费。
- **退款待处理期间额度不退回**：订单进入 `REFUND_PENDING` 后，额度**保持已扣减**的状态，直到渠道退款**成功（退回）或失败（收口）**为止。
- **不能重复发起**：`REFUND_PENDING` 只能由 `QueryAndFinalizeRefund` 收敛——重新发起退款会**重复扣减**并向网关重复退款（`payment_refund.go:213`）。
- **扣减/归还后要失效计费缓存**：退款扣减或归还余额后会失效该用户的计费缓存，否则网关在缓存 TTL 内仍按旧余额放行（`invalidateRefundBalanceCache`）。
- **订单类型受校验**：只接受 `balance` / `subscription`，其它 `order_type` 一律 `INVALID_ORDER_TYPE`（`payment_fulfillment.go:289,948`、`payment_order.go:132`）。
- **用户侧文案口径**：「申请退款」相关说明必须写成——**受理后额度先不退回**，直到渠道退款成功/失败收口。

> 白标商品中心（/shop，云猫）**不适用**这套口径：那边不建支付账本、不做退款与清结算（见 4.3）。

## 5. 对账与排障

### 5.1 使用记录里要看的字段

### 5.2 三类常见异常与处理

| 现象 | 判定 | 处理 |
|---|---|---|
| 「记录与锁价快照的实际分组或消费不一致」 | 记账与快照存在偏差（页面只呈现两份数据，不会改账） | 停止用户重复提交；用 request_id + 时间窗核对账本，必要时按对账流程纠错 |
| 扣了费但用量记录缺行 | 写日志与结算之间异常 | 账本（usage_billing）为准；Live 结算失败会保留 pending 状态并自动重试，重试金额固定不随时间增长 |
| 请求被拒但没扣费 | 缺价 / 鉴权 / 余额 / 参数类错误，这些**不换号也不结算** | 属预期行为；缺价先补价表再放量 |
| 请求返回 **404 `model_not_found`** | 该分组里**没有支持这个模型的账号**（不是缺价、不是余额问题） | 看 5.2.1：可能是模型退役，也可能是分组只挂了不支持该模型的账号 |

### 5.2.1 模型退役：GPT-5.5 的准确口径

**不要笼统写「GPT-5.5 已全面下架」**——这是事实错误。准确口径：

- **API Key 上游不受影响**，仍然可以正常调用 GPT-5.5。
- 因此，**只挂了 ChatGPT 订阅账号的分组**，放行 GPT-5.5 会返回 **404 `model_not_found`**。

- 管理端模型候选列表已按此口径写死（`frontend/src/i18n/locales/{zh,en}/admin/overview.ts`），**不要在文档或界面上另造一套说法**。

> 排障时先确认分组里挂的是哪类账号：**订阅账号分组**报 404 属于预期；**API Key 分组**报 404 要另查模型白名单与映射。
