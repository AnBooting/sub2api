# PRD 与技术规格模板

> 用途：需求明确后，每条需求按此模板产出文档，评审通过后才进入实现。
> 存放：`project-docs/requirements/REQ-XXX-<简述>.md`（PRD 与规格可合一份，也可拆两份）

---

## 二、技术规格模板

```markdown
# REQ-XXX 技术规格

## 1. 方案概述
一段话说清怎么做。附架构图（archify 产出，放 project-docs/architecture/diagrams/）。

## 2. 数据模型变更
### 2.1 迁移
| 编号 | 文件 | 内容 | 可回滚 |
|---|---|---|---|
| 244 | 244_xxx.sql | | |

> 迁移编号接在上游最新之后：**fork 已占 243，新增从 244 起**，不改写已有迁移。

### 2.2 Ent Schema
```go
// backend/ent/schema/<file>.go
field.String("xxx").Comment("...")
```
→ 改后必须 `go generate ./ent`（会重生成 backend/ent/ 下大量文件）

## 3. 后端改动
| 层 | 文件 | 改动 |
|---|---|---|
| 路由 | backend/internal/server/routes/ | |
| Handler | backend/internal/handler/ | |

| Service | backend/internal/service/ | |
| Repository | backend/internal/repository/ | |
| Wire | */wire.go | |
→ 改后必须重新生成 wire（cmd/server/wire_gen.go）

## 4. 前端改动
| 层 | 文件 | 改动 |
|---|---|---|
| API | frontend/src/api/ | |
| 类型 | frontend/src/types/index.ts | |
| 组件 | frontend/src/components/ | |
| 视图 | frontend/src/views/ | |

## 5. 接口契约
请求 / 响应 JSON 示例 + 错误码表

## 6. 关键逻辑
伪代码或流程图；说明并发、幂等、事务边界

## 7. 计费影响（涉及计费时必填）
| 项 | 改前 | 改后 |
|---|---|---|
| 国模单价 | | |
| Claude/GPT 单价 | | |
| 缺价行为 | | |

> 必须给**具体数值对比**，不接受「正确计费」这类描述。

## 8. 测试计划
| 层 | 用例 | 命令 |
|---|---|---|
| 单元 | | go test -tags=unit ./internal/... |

| 前端 | | corepack pnpm@9 exec vitest run |

## 9. 部署与回滚
部署步骤 / 回滚步骤 / 数据备份要求

## 10. 风险
| 风险 | 影响 | 缓解 |
|---|---|---|

## 11. 审查清单
- [ ] 无凭据泄漏
- [ ] 无越权
- [ ] 缺价拒绝（不零价、不兜底价）
- [ ] 迁移可回滚

- [ ] 鉴权缓存字段同步（若改了分组/账号结构）
- [ ] go build / vue-tsc / 测试全绿
```

---

## 三、协作约定

1. **先文档后代码**：PRD 与规格评审通过再写代码。
2. **一条需求一个分支**：`feat/REQ-XXX-<简述>`，从 `develop` 切出。
3. **规格里的「影响文件」就是 write scope**：多人并行按此划分，互不重叠。
4. **验收标准必须可执行**：写不出验证命令的标准不算数。
5. **计费改动必须给数值对比**。
6. **未确认的事写「未确认」**，不猜、不编。
7. **需求变更时先改文档再改代码**。
