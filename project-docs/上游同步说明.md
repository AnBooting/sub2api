## 1. 迁移编号重编号映射表（sync-migrations / task-16）

### 1.1 为什么必须重编号

`schema_migrations` 表以 **文件名** 作为主键记录已应用迁移（见 `backend/internal/repository/migrations_runner.go`），迁移按 **文件名字典序** 执行。因此「迁移编号」实际上是主键的一部分，两个分支各自占用同一号段时，编号不再唯一。

本 fork `develop` 与上游 `main`（v0.2.17）的实际占号：

| 号段 | 本 fork（develop） | 上游 main（v0.2.17） | 结论 |
|---|---|---|---|
| 242 | `242_drop_platform_check_constraints.sql` | `242_drop_platform_check_constraints.sql` + `242_group_i18n.sql` | 同一文件，无冲突。上游自身 242 重号属上游既有情况，**不在本轮处理** |
| 243 | `243_native_currency_pricing.sql` | `243_gemini_cached_contents.sql` | **冲突** |
| 244 | `244_api_key_group_links.sql` | `244_gemini_cached_contents_channel_usage.sql` | **冲突** |
| 245 | `245_group_scheduling_strategy.sql` | `245_gemini_cached_contents_mutation_lease.sql` | **冲突** |
| 246–250 | 本 fork 独有 | 上游无 | 暂不冲突，但会挡住上游未来从 246 起继续发号 |

上游 v0.2.17 的最高编号是 **245**，本 fork `develop` 的最高编号是 **250**。不处理的话，243/244/245 三个号段会同时承载两套完全无关的 DDL，迁移历史将无法审计。

### 1.3 相对执行顺序保持不变

重编号后仍是 251 → 252 → 253 → 254 → 255 → 256 → 257 → 258，**相对顺序与重编号前完全一致**。关键依赖：

- **258 依赖 252**：`252_api_key_group_links.sql` 建 `api_key_group_links` 表与 `api_key_group_links_authorization` CHECK；258 只做 `DROP CONSTRAINT IF EXISTS` + 重建放宽后的 CHECK，必须排在 252 之后。
- **256 → 257**：保持原 248 → 249 的先后（白标充值中心 → 视频任务表）。两者各建独立表、彼此无 DDL 依赖，顺序只为审计连续性保持不变。
- **253 → 254 → 255**：三者都只 `ALTER TABLE groups` 新增列，顺序不变。
- **251**：只改 `channel_model_pricing` / `usage_logs` 的列，与其余迁移无耦合。

### 1.4 改动内容（内容零改写）

- 8 个 SQL 文件**只改名**，DDL 逐字未动。
- 唯一的内容改动：`258_relax_group_link_authorization_check.sql` 的注释里两处编号引用 `244` → `252`（`Migration 244 constrained ...` / `does not rewrite 244`），以及补一句说明它原为 244、因 0.2.17 同步改名。
- `backend/migrations/README.md` 补了「编号分配现状（0.2.17 上游同步后）」与映射表，并给「禁止改迁移文件名」加了一条**一次性例外**说明。

### 1.5 迁移是否已在任何环境执行过 → 重命名安全

- 这 8 个迁移**只存在于 fork 的 `develop` 分支**，本项目尚未做过生产部署（task-16 既定事实，已由 lead 核实），任何环境的 `schema_migrations` 表里都不存在这些文件名。
- 因此重命名既不会导致「同一逻辑被执行两次」，也不会触发 runner 的 checksum mismatch（runner 按**文件名**判定是否已应用）。
- 兜底说明：若将来某个环境确实执行过旧文件名，需要手工把 `schema_migrations` 中对应行的 `filename` 改名后再上线；当前无此场景。
