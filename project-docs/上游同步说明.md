### 1.5 这些迁移在各环境是否执行过 —— **无法从仓库确认**（更正此前的错误表述）

**此前这里写的是**「这 8 个迁移未在任何环境执行过，任何环境的 `schema_migrations` 里都不存在这些文件名，因此重命名安全」。**这个说法不成立，现更正**：

- 迁移是否执行过只体现在各环境数据库的 `schema_migrations` 表里（按**文件名**记录），**仓库里查不到**。本项目没有权威的环境清单，所以「没有任何环境执行过旧文件名」这件事**无法从仓库确认**。
- 已有反证：据同事转述的**部署聊天记录**，曾有环境升级到 **250**（旧编号的最后一条）。若该环境确实执行过 243–250，它的 `schema_migrations` 里就是**旧文件名**；升级到改名后的版本时，执行器按新文件名查不到记录 → 重放 → 撞同名约束（SQLSTATE 42710）→ **服务启动直接失败**。
- 本项目尚未做过正式生产部署，所以「生产库是否受影响」同样**无法从仓库确认**。
- 结论：**重编号对「已执行过旧文件名」的环境是破坏性的**，不能按「没执行过」来假设。处置分两层：
  - **代码层**：执行器对**明确登记的改名迁移**做受限容错（见 §1.10），让这类环境能启动起来；
  - **运维层**：按 §1.10 的步骤把新文件名写回 `schema_migrations`，彻底消除每次启动的重试。

### 1.10 旧库升级：受限容错与运维步骤（task-39）

#### 1.10.1 代码侧：受限容错

执行器按**完整文件名**判断迁移是否已应用，所以旧库（`schema_migrations` 里记的是 `243_…`）遇到新文件名 `251_…` 会被判为「未应用」而重放，撞上已存在的同名约束 → **服务启动直接失败**。

现在执行器对这种「改名迁移在旧库上的重放」有**受限容错**（实现见 `backend/internal/repository/migrations_renamed_replay.go`）：

- **只对明确登记的 8 个改名迁移生效**（`renamedMigrationReplayRules`），逐条登记「旧文件名 + 旧文件 SHA256 + 允许的重复错误码」，不做任何模糊匹配；
- 允许的错误码按每条迁移的 DDL **逐个推导**：
  - `251_native_currency_pricing.sql`：第 2 条 `ADD CONSTRAINT` 没有 `IF NOT EXISTS` → 重跑撞 **42710**（重复约束）；
  - `252_api_key_group_links.sql`：`ADD CONSTRAINT` → **42710**；`CREATE TABLE` / `CREATE INDEX` → **42P07**（重复表）。唯一键冲突 **23505 不登记**——它只出现在「库被部分应用」的异常状态，必须显式失败；
  - `253`–`258`：DDL 本身可重跑（`ADD COLUMN IF NOT EXISTS` / `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` / `pg_constraint` 守卫的 DO 块 / `DROP CONSTRAINT IF EXISTS` 后重建），**不产生重复对象错误**，因此不登记任何容错码；其中 258 是「先删后建」，重跑不会撞 42710；
- 命中时还要校验**当前文件内容的 SHA256 与登记的旧校验和一致**——迁移内容在改名之后被改过就**不容错**，照旧报错退出；
- **重复对象错误本身不足以证明旧迁移执行过**：迁移正文在事务里执行，251 的第 2 条 `ADD CONSTRAINT` 撞 42710 会让**整份迁移回滚**，第 3 条 `ALTER TABLE usage_logs ADD COLUMN IF NOT EXISTS pricing_snapshot` 从未执行。若此时按「已生效」放行，库里会永久缺这一列，而服务照常启动。因此放行前必须**向数据库取证**：在持有 advisory lock 的连接上查 `schema_migrations` 是否存在**旧文件名**记录，且其 checksum 与登记的旧校验和逐字一致；
- 取证成立后**补记新文件名**（`INSERT INTO schema_migrations (filename, checksum)`），让后续启动不再重复执行这份迁移；启动日志打一条 WARN（`renamed migration replay tolerated on legacy database`，字段 `migration` / `previous_filename` / `sqlstate`）；
- **以下情况一律照旧失败、中止启动**：迁移不在登记表；错误码不在该迁移允许集合里；错误里识别不出 SQLSTATE；当前文件内容与登记校验和不符；**查不到旧文件名记录**；**旧记录 checksum 与登记值不一致**；**取证查询本身报错**；**补记新文件名失败**。缺证据就不放行，不做任何猜测或降级。

#### 1.10.2 运维升级步骤

1. **先备份**：全量备份数据库（`pg_dump`）并确认可恢复。改名迁移在启动期执行 DDL，备份是唯一兜底。
2. **升级**：发布新版本并启动。服务启动时执行迁移；对执行过旧名迁移的环境，`251` / `252` 会命中容错并打 WARN，**服务应能正常起来**。
3. **看告警**：在启动日志里搜 `renamed migration replay tolerated on legacy database`。
   - 每条 WARN 的 `migration` 是新文件名、`previous_filename` 是旧文件名、`sqlstate` 是命中的错误码（`42710` 重复约束 / `42P07` 重复表）；
   - **出现**这类告警 → 该库确实执行过旧名迁移，继续第 4 步对账；
   - **没有**这类告警、也没有迁移失败 → 该库本来就没执行过旧名迁移，无需处理。
4. **确认新文件名已补记**（容错路径自动完成，此步只是核对）：取证成立后执行器会写入新文件名记录，所以**不会**每次启动都再撞一次。核对：

   ```sql
   SELECT filename, checksum, applied_at
   FROM schema_migrations
   WHERE filename LIKE '25%'
   ORDER BY filename;
   ```

   预期：`251`–`258` 中新名记录存在。若某条 WARN 对应的新文件名**没有**记录，说明补记失败（此时启动应当已经报错退出，不会静默）——按第 1 步回滚并带上日志找开发确认。

   > 历史说明：旧版本容错**不写** `schema_migrations`，需要按上表手工改名；现在已改为自动补记，**不要再手工改 `schema_migrations`**。若某库仍残留旧文件名行（例如手工改过一半），执行器会同时看到旧名与新名记录，不影响启动，但建议清理旧名行保持整洁。

5. **复核**：重启一次服务，确认启动日志里**不再**出现该 WARN（新文件名已补记，不会再重放）。

6. **如果启动直接失败**（没有 WARN、而是报错）：说明撞到的错误不在登记的容错范围内（例如迁移文件在改名之后被改过，或库里是「部分应用」的异常状态）。此时**不要**手工改 `schema_migrations` 蒙混过关：按第 1 步回滚到备份，并带上完整错误日志找开发确认。

#### 3.3.1【D5】gemini 显式上下文缓存（`d5a802f84`）—— 本轮最大的一笔，也是唯一新增计费面

- **上游改了什么**：新增 `/v1beta/cachedContents` 的创建/列表/查询/改期/删除五个接口（迁移 `243_gemini_cached_contents`）。网关自建缓存 ID 并绑定「上游资源名 + 持有账号 + 创建它的 API Key」。计费规则：创建时**一次性**收取缓存输入 token 费 + 整个有效期的存储费；延长按库中实际推进的时长收费，**纯存储费不算一次请求**；缩短与删除不退费。存储单价取自定价覆盖文件的 `cache_storage_cost_per_token_per_hour`，未配置该价的模型**拒绝创建**。扣费前校验余额/订阅额度/API Key 额度并登记**不封顶的在途预留**，不足时删除上游缓存、只收输入费。有效期上限 `gateway.gemini_cached_content_max_ttl_seconds`（默认 86400）。
- **我们的对应功能**：我们的锁价快照（`pricing_snapshot.go`）只覆盖**单次请求**的锁价语义；「存储费按整段有效期一次性收取」这种**跨请求、跨时间的预收**语义在我们的模型里没有对应物。
- **合并后行为（本轮已改）**：gemini 显式缓存的**写侧**不再走「live 价卡 + 实时倍率」，而是与读侧**共用请求建立时冻结的价卡与冻结倍率**（`prepareSharedGatewayLockedBillingWithErrorWriter` + `bindSharedGatewayLockedBillingAccount`），预留金额 = 冻结价卡 × 实际上游 token 数 × 冻结倍率，最终记账走 `RecordUsage` 的锁价分支 → **预留 ≡ 记账**。冻结价卡缺存储单价 → **在上游建缓存之前**拒绝（`pricing_unavailable`）；冻结价卡要求 input/output/cache_read/cache_write 四项齐备（比上游更严）。
- **是否需要我们再决策**：**已定**。① 界面/手册说明「创建显式缓存会一次性预收存储费」；② 「缺价不得放行」与上游「未配置存储价则拒绝创建」**结论一致**，我们更严；③ 在途预留下限沿用上游口径。④ **边界澄清**：显式缓存的写入在 Gemini 上按官方规则**计入 input 用量**，与共享契约里的 `cache_write` / `cache_write_1h` kind（面向渠道/分组手工卡与 Anthropic 风格缓存写入）**不是同一件事**；⑤ **幂等键口径**：锁价路径的 `usage_logs.request_id` 为 `locked:<id>`（与其它锁价消费同语义），`gcache` 标识放进 `session_id`，费用行仍可按缓存 ID 检索。
