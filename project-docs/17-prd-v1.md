## 3. REQ-009 调度并发修正 + 诊断面板（P0）

**背景**：DeepSeek（42 个 API Key）、OpenAI（API Key + OAuth）账号出现「部分账号不被路由、部分账号压力过大」。源码中抢占并发槽位的上限用 `concurrency`，而选号时的负载率分母优先用 `load_factor`，两个值不一致时调度结果失真。上游没有官方 RPM/TPM 限制。

**目标**：并发数成为唯一硬上限；账号间负载均衡；保留会话粘性；遇到上游 429 自动降压。

| 编号 | 功能需求 |
|---|---|
| F-9.1 | 账号同时进行的请求数**永不超过**其 `concurrency`。选号时的负载率统一以 `concurrency` 为分母；`load_factor` 只作为「被选中的权重」，不影响上限 |
| F-9.2 | 无粘性的请求在可用账号中按「负载率低 + 权重高」优先选择，避免长期闲置账号 |
| F-9.3 | **粘性保留**：同一会话优先回到原账号；原账号满并发时最多等待 **3 秒**（可配），仍满则换账号并把粘性改绑到新账号 |
| F-9.4 | **429 自适应**：账号收到上游 429 后，有效并发降为原值的一半（至少 1），冷却 **15 秒**（可配）后逐步线性恢复到原值；连续 429 继续减半 |
| F-9.5 | 管理员修改并发数、负载因子后 **1 秒内生效**，不需要重启 |
| F-9.6 | **调度诊断面板**（管理端）：按分组/平台列出每个账号的配置并发、当前占用、有效并发（含 429 降级状态）、近 5 分钟请求数和 429 次数、粘性会话数；配置异常（并发为 0、负载因子与并发差异过大）标红 |

**验收标准**
- AC-9.1 压测：并发数设 N 的账号，在 3N 并发请求下，任意时刻实际占用 ≤ N（以诊断面板和 Redis 槽位双重核对）
- AC-9.2 10 个同配置账号、无粘性请求，5 分钟内各账号请求量偏差 ≤ 30%
- AC-9.3 粘性会话：原账号空闲时 100% 回到原账号；原账号满时等待不超过 3 秒后换号，下一次请求落到新账号
- AC-9.4 模拟上游 429：该账号有效并发减半，15 秒后开始恢复，面板可见状态变化
- AC-9.5 修改并发后 1 秒内新请求按新值调度

**边界**：并发数为 0 的账号视为不可调度，并在面板标红；所有账号都满且等待超时时，进入 REQ-011 兜底流程。

## 4. REQ-011 兜底分组链（P0）

**背景**：原分组没有可用账号或上游失败时，请求直接报错。需要按顺序把请求转到其他分组。

| 编号 | 功能需求 |
|---|---|
| F-11.1 | 管理员配置**兜底分组池**（允许被用作兜底的分组）和**全局默认兜底链**（有序） |
| F-11.2 | 管理员可为单个分组配置覆盖链，优先于全局默认链 |
| F-11.3 | 用户可在自己的 API Key 上，从兜底分组池中选择分组并排序；未选择时使用「分组覆盖链 → 全局默认链」 |
| F-11.4 | 触发条件：① 选号阶段没有可调度账号（全部禁用、限流、满并发且等待超时）；② 上游返回 5xx 或 429 且重试耗尽；③ 上游返回「模型不支持 / model not found」 |
| F-11.5 | **不触发**：4xx 参数错误、鉴权失败、用户余额不足、内容审核拒绝 |
| F-11.6 | 按链的顺序依次尝试，前一个也满足触发条件才换下一个；链跑完仍失败返回原始错误 |
| F-11.7 | 计费按**实际提供服务的分组倍率**；倍率更高也照常扣费 |
| F-11.8 | 兜底不受用户分组权限限制 |
| F-11.9 | 用户与管理员的使用记录标注「兜底」和实际分组名 |
| F-11.10 | 新建 API Key 未选择分组时，自动绑定管理员指定的**默认分组**（具体分组按线上数据确定，默认候选为现有 1x 倍率分组） |

**验收标准**
- AC-11.1 原分组所有账号禁用 → 请求成功落到链上第一个可用分组，记录显示「兜底 / 分组名」，按该分组倍率扣费
- AC-11.2 上游返回 400 参数错误 → 不兜底，直接返回
- AC-11.3 用户在 Key 上自选的链优先于全局链生效
- AC-11.4 **一次请求只扣一次费**：已向上游发出但失败的尝试不计费
- AC-11.5 不选分组新建 Key → 自动绑定默认分组

**边界**：兜底链里出现原分组自己或重复分组时自动去重；链中分组被删除或停用时跳过。流式请求只在**尚未向客户端输出任何内容**前允许兜底。

## 6. REQ-012 图片/视频能力对齐 new-api（P1）

**背景**：现存三类问题：按 new-api 格式调用报 404 或格式错误、扣费不对、部分模型完全不支持。暂无报错样例，按 new-api 能力整体设计，再在测试服务器上逐个模型实测。

**模型范围**

| 模型 | 调用方凭据类型 | 备注 |
|---|---|---|
| Sora | API Key | 目前仅 Azure 渠道可用 |
| Veo | API Key | |
| 可灵 | API Key | |
| Seedance / 豆包 | API Key | |
| Grok | API Key + OAuth | |
| GPT-image | OAuth | |
| Gemini 图片 | API Key | |

| 编号 | 功能需求 |
|---|---|
| F-12.1 | 提供 new-api 统一格式：`POST /v1/video/generations` 提交任务，按任务 ID 查询状态与结果 |
| F-12.2 | 同时支持各厂商原生接口透传 |
| F-12.3 | 本地任务表记录每个视频任务；后台主动轮询上游，不依赖客户端来查 |
| F-12.4 | 任务**成功后**自动扣费；失败或超时（最长 **30 分钟**）**不扣费** |
| F-12.5 | 结果直接返回上游链接，不转存 |
| F-12.6 | 任务记录保留 **30 天** |
| F-12.7 | 计费：管理员按「模型 × 分辨率 × 时长」配置价格，每个模型选「按秒」或「按次」；初始价格参考 new-api 与官方价，由技术负责人录入 |

**验收标准**

- AC-12.2 构造上游失败、超过 30 分钟超时：任务标记失败，余额不变
- AC-12.3 客户端从不查询的任务，也能在完成后被自动扣费
- AC-12.4 未定价模型请求被拒绝，且上游没有收到请求
- AC-12.5 用 new-api 的典型客户端请求格式调用，不再出现 404 或格式错误

**边界**：提交时预检余额，余额不足直接拒绝；任务完成时余额不够，仍记账为欠费并停用该 Key 的新任务（待评审确认，见 §11 #3）。

## 8. REQ-010 云猫卡网充值（P1）

**背景**：店铺在云猫寄售（catfk.com，SaaS，手续费 1.8%）。云猫只提供**支付成功回调**，没有下单和查单 API。支付方式为微信、支付宝；购买页可被 iframe 嵌入。历史订单约 300 条（2026-09～10），可导出 CSV，部分订单对不上站内用户，卡密不过期。

| 编号 | 功能需求 |
|---|---|
| F-10.1 | 管理员在后台配置商品：名称、售价（1–198 元）、权益类型（额度 / 订阅 / 并发）、权益数值、对应云猫商品链接；无限购 |
| F-10.2 | 商品展示在**现有充值页**，按「余额 / 订阅 / 并发额度」分标签页；售价展示**含 1.8% 手续费**（买家承担） |
| F-10.3 | 用户点击购买，在站内弹窗中以 iframe 打开云猫购买页，并带上站内用户标识（具体方式依回调文档确定） |
| F-10.4 | 接收云猫支付回调：校验签名和来源，按云猫订单号**幂等**处理，写入系统订单表 |
| F-10.5 | 能对应到站内用户的订单：**默认直接入账**，同时生成一条已使用的兑换码记录；用户也可选择领取兑换码 |
| F-10.6 | 对不上用户的订单：只生成兑换码，买家凭码在站内自行兑换 |
| F-10.7 | 兑换码可转赠，售出时实时生成，不过期 |
| F-10.8 | 导入历史订单 CSV：生成可兑换记录，**不自动给任何人入账**；重复导入按订单号去重 |
| F-10.9 | **二期（另行评审）**：用自己的店铺下小额测试单抓包，评估把云猫非公开下单接口封装成站内原生页面。风险：可能违反云猫条款导致封店、云猫改版即失效、风控验证码。需负责人确认风险后才开工 |
| F-10.10 | 退款：回调无法触发退款，**一律人工处理**，扣减使用 REQ-016 的「普通余额调整」 |

**验收标准**
- AC-10.1 小额真实订单：付款后 10 秒内到账，订单状态为已支付
- AC-10.2 同一回调重复推送 3 次只入账一次
- AC-10.3 伪造签名的回调被拒绝并记录
- AC-10.4 对不上用户的订单生成兑换码，兑换后权益正确
- AC-10.5 导入 300 条历史订单，重复导入不产生重复记录

**阻塞**：云猫回调文档（字段、签名算法、来源 IP、是否支持自定义参数传用户标识）。

## 9. REQ-016 管理员补单 / 普通余额调整（P1）

**背景**：现有管理员充值弹窗只能加减余额。用户付款未到账时直接加余额，之后回调晚到会**重复入账**。

| 编号 | 功能需求 |
|---|---|
| F-16.1 | 管理员「充值」弹窗增加两种模式单选：**充值订单补单**、**普通余额调整** |
| F-16.2 | **补单**：选择该用户一笔未到账的充值订单（含云猫订单），**必须填写云猫订单号或上传付款凭证**，确认后订单标记为已支付并入账，订单结清 |
| F-16.3 | 补单后原回调晚到：按订单号识别为已处理，忽略，不重复入账 |
| F-16.4 | **普通余额调整**：用于赠送、调账、人工退款扣减，不关联订单；界面提示「不会结清充值订单，处理未到账请使用『充值订单补单』」 |
| F-16.5 | 两种模式**都不需要审批**，但记录操作人、时间、金额、备注、凭证 |
| F-16.6 | 订单详情页展示补单记录：操作人、时间、订单号/凭证、备注 |
| F-16.7 | 弹窗显示用户当前余额和操作后余额 |

**验收标准**
- AC-16.1 补单后余额正确增加，订单状态为已支付，详情页可见补单记录与操作人
- AC-16.2 补单后再推送该订单的回调，余额不变
- AC-16.3 未填订单号且无凭证时无法提交补单
- AC-16.4 普通余额调整不改变任何订单状态，余额流水记录操作人

| 官方版升级到 fork 迁移不兼容 | 线上数据风险 | 测试服务器演练 + 全量备份 + 回滚预案 |
| 兜底导致重复扣费 | 用户损失 | AC-11.4 强制一次请求只扣一次 |
| 视频价格初值不准 | 亏损或投诉 | 上线前技术负责人复核价格表 |
